## Architecture summary

The UI uses Vite and React 18 with feature registration through a page/menu registry. Registration is currently compile-time discovery, not lazy route loading: `features/index.ts` imports every feature's `register.tsx`, and those registration modules synchronously import their screen components. `AppShell.tsx` also synchronously imports the gate screens, workspace screens, POS screens, KDS, settings modal, and other major views. `App.tsx` uses `React.lazy()` only for the development-only DevToolbar.

The main Vite configuration has no `build.rollupOptions.manualChunks`, route-level dynamic import policy, bundle budget, or performance plugin. The tablet configuration has a separate entry and output directory but likewise has no explicit chunk strategy. The application does contain `react-window` as a dependency, but dependency presence alone does not establish virtualization across the major data views.

The largest observed production build artifact was a single `dist/assets/index-Bx84n8Op.js` bundle of approximately **2.10 MB** (about **522 KB gzip**), followed by a single CSS asset of approximately **632 KB** (about **80 KB gzip**). Vite transformed 1,074 modules and emitted a warning that some chunks exceeded 500 KB.

## Findings

### PERF-01 — Major feature routes are not deliberately split from the initial JavaScript path

**Evidence:** `features/index.ts` synchronously imports all 24 feature registration modules. Feature registration modules synchronously import their page components. `AppShell.tsx` synchronously imports `SetupWizard`, `StaffLoginScreen`, `WorkspaceHome`, `RetailPosScreen`, `PosScreen`, `KdsScreen`, `WorkspaceSettingsModal`, `LicenseActivationScreen`, `CreatePinScreen`, and `SessionLockScreen`. `App.tsx` lazily imports only the development-only DevToolbar.

**Impact:** A user opening a single POS or workspace flow can pay substantial parse, compile, and download cost for unrelated reports, purchasing, KDS, settings, inventory, and management screens. This increases startup time and memory use, particularly on lower-powered terminals and tablet hardware. The build does emit some secondary chunks, but the major route tree is not intentionally lazy-loaded.

**Recommendation:** Make page registrations lazy-loadable while preserving the registry API, or split the registry into lightweight metadata plus dynamic component loaders. Keep authentication/setup gates in the critical path, but defer secondary features until navigation. Add a Suspense fallback and route-level chunk-load error recovery. Measure cold-start and first-interaction time before and after the change.

**Status:** Open · P1 initial-load performance

### PERF-02 — The production entry bundle exceeds a practical performance budget

**Evidence:** The fresh production build completed successfully but emitted a JavaScript asset of approximately 2.10 MB (522 KB gzip) and a CSS asset of approximately 632 KB (80 KB gzip). Vite reported chunks above its 500 KB warning threshold. `package.json` has no bundle-budget or size-regression script, and `vite.config.ts` does not define explicit chunking or budget enforcement.

**Impact:** Bundle growth can proceed unnoticed until startup becomes materially slow. The cost is paid even when a terminal uses only one workspace and increases code-cache pressure on every release.

**Recommendation:** Define budgets for initial JS/CSS, route chunks, and total compressed assets. Fail CI on meaningful regressions with a documented exception process. Track raw and gzip/brotli sizes per build, then split large domains and remove unused code/assets from the initial path.

**Status:** Open · P1 release-performance governance

### PERF-03 — Retail serial-tracking lookup performs one IPC request per unique cart SKU

**Evidence:** `RetailPosScreen.tsx` derives `uniqueSkus` from cart lines and calls `getProductTrackSerial(sku)` independently for every SKU whose state is unknown. The effect therefore performs N IPC calls for N unique SKUs. `pendingTrackFetchRef` prevents duplicate calls for the same SKU but does not batch them.

**Impact:** Adding a cart containing many distinct products creates a burst of serial-tracking IPC/database requests. IPC overhead and repeated database work grow linearly with cart diversity and can compete with checkout interactions.

**Recommendation:** Add a batch command/API accepting a bounded SKU array and return a map, or expose tracking capability in the product payload already loaded by the grid. Cache results by store/session and invalidate only when product configuration changes. Add a contract test for batching and a performance test at realistic cart sizes.

**Status:** Open · P1 IPC efficiency

### PERF-04 — Cart resize updates React state and localStorage on every mousemove

**Evidence:** `RetailPosScreen.tsx` registers a document-level `mousemove` handler during resize. Every event reads layout via `getBoundingClientRect()`, computes a width, calls `setRetailCartWidth`, and writes `retail-cart-width` to `localStorage`. There is no requestAnimationFrame throttle or deferred persistence.

**Impact:** High-frequency pointer events can trigger repeated renders of the large retail screen and synchronous storage writes. Layout reads followed by state/layout work can cause jank while dragging, especially on slower terminals.

**Recommendation:** Store the live width in a ref/CSS custom property during the drag and schedule at most one update per animation frame. Persist only on mouseup (or with a debounced write). Avoid repeated layout reads where possible by using the initial panel geometry and pointer delta. Add a drag performance regression test or browser trace budget.

**Status:** Open · P2 interaction performance

### PERF-05 — No deliberate production route-level chunk strategy is configured

**Evidence:** `vite.config.ts` configures React, aliases, server, and Vitest but has no `build.rollupOptions.output.manualChunks`, route chunk policy, or bundle analyzer/budget. `vite.tablet.config.ts` only changes the entry and output directory. The only discovered production-relevant dynamic imports are isolated utilities such as the updater/event modules; Vite also reported dynamic/static import mixing warnings, so those imports do not provide a reliable route-level split for the major feature tree.

**Impact:** Build output depends on incidental bundler behavior rather than deliberate domain boundaries. A future dependency added to one screen can increase the common entry chunk for every user.

**Recommendation:** Establish stable domain chunks for sales/POS, inventory, reports, settings, and optional integrations, or use lazy page components to let Rollup form route chunks. Verify that shared dependencies remain shared and that critical POS dependencies are not duplicated across chunks.

**Status:** Open · P2 architecture/performance

### PERF-06 — Performance measurement is not an enforced part of the development or release loop

**Evidence:** Existing scripts and `docs/benchmarks.md` provide profiling/benchmark documentation, but the UI package has no web-vitals/RUM dependency, React Profiler capture, startup budget test, route-load timing assertion, or bundle-size gate. `logged-invoke` logging can expose IPC timing during development, but it is not a release-level performance metric or regression gate.

**Impact:** The team can identify a regression only after users report slow startup or interaction. There is no stable baseline for cold start, route transition, render commits, IPC latency, or memory behavior across desktop and tablet targets.

**Recommendation:** Define a small set of measurable budgets: time to first shell, time to interactive POS, route chunk load, long tasks during checkout, IPC p95 latency, and initial bundle gzip size. Collect development/CI traces without sending production-sensitive data, and publish results alongside release checks.

**Status:** Open · P2 observability gap

### PERF-07 — Large-list virtualization is not an established cross-feature contract

**Evidence:** `react-window` is declared in `ui/package.json`, but the inspected registry and major screen paths do not define a shared list policy or demonstrate that audit logs, products, transactions, reports, and transfer histories all use virtualization or bounded pagination. Several audited screens load and render collections directly; `AuditLogScreen` uses offset loading and inventory screens contain list/table surfaces.

**Impact:** A large tenant dataset can cause excessive DOM nodes, layout work, memory use, and slow filtering. Dependency presence does not protect screens that render plain arrays.

**Recommendation:** Set explicit limits and pagination rules for every unbounded collection, then use virtualization only where row height and interaction semantics support it. Add a shared data-list primitive with loading/empty/error states and performance tests at 1k/10k-row fixtures.

**Status:** Open · P2 scalability risk

### PERF-08 — Product and category loading can perform multiple independent requests on every retail workspace/session load

**Evidence:** `RetailPosScreen.tsx` calls `listProductsScoped(token)` and `listCategories()` independently whenever the session token changes, with retry repeating both calls. The screen then derives filtering, category labels, low-stock counts, and pages in React. This is functionally straightforward but lacks a cache or request deduplication shared with other product/category consumers.

**Impact:** Switching workspaces, remounting POS, or retrying after a transient failure can repeat large product/category payloads and duplicate work across screens. The cost grows with catalog size and terminal count.

**Recommendation:** Add a scoped catalog cache with request deduplication and explicit invalidation after product/category mutations. Return only fields needed for the product grid or provide a paginated/search API for large catalogs. Instrument payload bytes and request latency before optimizing.

**Status:** Open · P2 data-loading efficiency

### PERF-09 — Chart rendering and canvas assets lack a documented accessibility/performance policy

**Evidence:** Canvas charts perform full redraws from React data/formatter dependencies and use inline minimum-height styles. The components are lightweight for small datasets, but no data-size cap, redraw budget, resize debounce, or chart rendering measurement was found in the inspected performance infrastructure. Large report datasets can increase draw and text-label work.

**Impact:** Reports can spend unnecessary main-thread time redrawing charts on filter changes or resize events. Without a policy, each chart implementation may scale differently and regress independently.

**Recommendation:** Bound or aggregate chart points before rendering, coalesce redraws with requestAnimationFrame, avoid drawing every label at high cardinality, and add a chart fixture benchmark for small/medium/large datasets. Keep the accessible data representation from the accessibility audit synchronized with the performance limit.

**Status:** Open · P3 reporting performance

### PERF-10 — Performance validation is build-centric and lacks runtime desktop/tablet coverage

**Evidence:** The production build and typecheck pass, and profiling scripts exist, but no discovered CI gate runs browser performance traces, cold-start measurements, route chunk budgets, IPC p95 checks, or tablet-specific runtime benchmarks. The separate tablet Vite build has no corresponding size/performance report in the inspected scripts.

**Impact:** Desktop build success does not prove acceptable startup or interaction performance on the intended POS terminal and tablet hardware. Regressions in one target can remain invisible.

**Recommendation:** Add a small repeatable Playwright performance smoke suite for desktop and tablet: startup to interactive, route transition, product search, add-to-cart, checkout open, and KDS refresh. Store only aggregate timings and fail on large regressions with environment-aware thresholds.

**Status:** Open · P3 QA gap

## Positive controls observed

- Production build and TypeScript compilation complete successfully.
- Vite emits a chunk-size warning rather than silently hiding large output.
- DevToolbar is already guarded behind a development-only lazy import and is not part of the intended production path.
- Retail product/category loads use an abort controller to prevent stale requests after token changes or retry.
- Serial tracking uses a pending-SKU set to avoid duplicate requests for the same SKU.
- Retail product filtering and pagination are memoized, and catalog products are capped to a page size in the screen.
- `react-window` is available for virtualization where a feature chooses to use it.
- Profiling scripts and benchmark documentation exist, providing a foundation for formal budgets.

## Recommended remediation order

1. **PERF-01/PERF-02/PERF-05:** Introduce route-level code splitting and enforce compressed bundle budgets.
2. **PERF-03/PERF-04:** Batch serial tracking and throttle/defer retail resize work.
3. **PERF-06/PERF-10:** Add runtime metrics and desktop/tablet performance smoke gates.
4. **PERF-07/PERF-08:** Standardize large-list limits, virtualization, and catalog request caching.
5. **PERF-09:** Bound and measure chart redraw/render cost.
