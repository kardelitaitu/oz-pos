## How the Migration Runner Works

```
On boot:
  1. Ensure schema_migrations table exists
  2. Load applied migrations (id + checksum) from schema_migrations
  3. For each migration in ALL registry:
     ├── Already applied + checksum matches → skip (verified)
     ├── Already applied + no checksum → backfill checksum
     └── NOT applied → apply in transaction, record id + checksum
```

Key behaviors:
- Runner only checks migrations IN the registry — old IDs in the DB are ignored
- Each migration runs in a transaction — all-or-nothing
- Checksum drift = hard error (DB-02)
- `execute_batch` runs all SQL in the migration file

## Root Cause: Missing Seed Data

### The Problem

The init SQL was generated by replaying all 131 old migrations on an
in-memory SQLite and dumping the **schema structure** (tables, indexes,
triggers). However, the old migrations also contain **seed data** —
`INSERT OR IGNORE INTO` statements that populate essential lookup tables.

The SQLite dump only captures DDL (CREATE TABLE/INDEX/TRIGGER), not DML
(INSERT). This means the init SQL is missing ~30 seed INSERT statements
that the old migrations applied.

### Why Tests Fail

Tests like `assignment_for_user_loads_scoped_lists` insert into
`assignment_workspaces` with `workspace_key = 'retail-pos'`. In the old
code, migration 128 seeds `retail-pos` into the `workspaces` table, so the
FK constraint `assignment_workspaces.workspace_key → workspaces.key` is
satisfied.

In the new code, the init SQL creates the tables (including FK constraints)
but does NOT seed the workspace data. The FK constraint fails because
`workspaces` is empty.

### Affected Seed Data

The old migrations seed data into these tables:

| Table | Source Migration | Purpose |
|-------|-----------------|---------|
| `currencies` | 006 | USD/IDR currency definitions |
| `store_profiles` | 025 | Default store profile |
| `loyalty_tiers` | 031 | Default loyalty tiers (Bronze/Silver/Gold) |
| `workspaces` | 035, 048, 128 | restaurant-pos, store-pos, inventory, admin, kds, retail-pos |
| `workspace_screens` | 035 | Navigation items per workspace |
| `workspace_types` | 060 | Restaurant/Store/Inventory/Admin workspace types |
| `workspace_type_screens` | 060 | Screen assignments per type |
| `workspace_instances` | 060, 120, 121 | Default workspace instances |
| `user_workspace_instances` | 060 | User-instance bindings |
| `role_workspace_types` | 060 | Role-type access |
| `user_store_access` | 060 | User-store access |
| `tenant_subscription` | 061 | Default subscription tier |
| `settings` | 075 | Default currency setting |
| `inventory_locations` | 078 | Default inventory locations |

### Verification

```
Old code (131 migrations): assignment test PASSES
  → migration 128 seeds retail-pos → FK satisfied

New code (1 init, no seeds): assignment test FAILS
  → no retail-pos in workspaces → FK violated

Python comparison: schemas are IDENTICAL (92 tables, 121 indexes, 4 triggers)
  → the issue is ONLY missing seed data, not schema differences
```

## Solution: Include Seed Data in Init SQL

The init SQL must include essential seed data after the schema DDL. This
makes it a complete "bootstrap" migration that creates a fully functional
database from scratch.

### Seed Data to Include

```sql
-- ====================================================================
-- SEED DATA
-- ====================================================================

-- Currencies
INSERT OR IGNORE INTO currencies (code, numeric_code, name, minor_exponent, symbol) VALUES
    ('USD', '840', 'US Dollar', 2, '$'),
    ('IDR', '360', 'Indonesian Rupiah', 0, 'Rp');

-- Default store profile
INSERT OR IGNORE INTO store_profiles (id, name, is_primary) VALUES
    ('default', 'Default Store', 0);

-- Loyalty tiers
INSERT OR IGNORE INTO loyalty_tiers (id, name, min_points, points_per_unit, earn_multiplier, colour, sort_order) VALUES
    ('tier-bronze', 'Bronze', 0, 100, 1.0, '#CD7F32', 1),
    ('tier-silver', 'Silver', 1000, 100, 1.5, '#C0C0C0', 2),
    ('tier-gold', 'Gold', 5000, 100, 2.0, '#FFD700', 3);

-- Workspaces
INSERT OR IGNORE INTO workspaces (id, key, name, description, icon) VALUES
    ('ws-restaurant-pos', 'restaurant-pos', 'Restaurant POS', '...', 'restaurant'),
    ('ws-store-pos', 'store-pos', 'Store POS', '...', 'store'),
    ('ws-inventory', 'inventory', 'Inventory Management', '...', 'inventory'),
    ('ws-admin', 'admin', 'Admin', '...', 'settings'),
    ('ws-kds', 'kds', 'Kitchen Display', '...', 'kitchen'),
    ('ws-retail-pos', 'retail-pos', 'Retail POS', '...', 'store');

-- ... (workspace_screens, workspace_types, workspace_instances, etc.)
```

### What NOT to Include

- Data migration INSERTs (INSERT INTO xxx_new SELECT FROM xxx) — these are
  one-time transformations that don't apply to a fresh schema
- User/role seed data — these are app-level seeds, not schema seeds
- KDS order targets — runtime data, not seed data

## Existing Dev Database Migration Path

```
Existing DB (131 old migrations applied)
    │
    ├── schema_migrations contains: 001_sales.sql, ..., 136_processed_webhooks.sql
    ├── Tables already exist with full schema (including FKs from migration 117)
    │
    ▼
New code boots → runner loads ALL = [20260813_init.sql]
    │
    ├── 20260813_init.sql NOT in schema_migrations → apply it
    ├── SQL: CREATE TABLE IF NOT EXISTS ... → no-op (tables exist)
    ├── SQL: CREATE INDEX IF NOT EXISTS ... → no-op (indexes exist)
    ├── SQL: CREATE TRIGGER IF NOT EXISTS ... → no-op (triggers exist)
    ├── SQL: INSERT OR IGNORE INTO ... → no-ops (seed data already exists)
    ├── INSERT INTO schema_migrations → recorded with checksum
    │
    ▼
✅ Schema unchanged, migration recorded, old IDs silently ignored
```

```
Fresh DB (no schema_migrations)
    │
    ▼
New code boots → runner loads ALL = [20260813_init.sql]
    │
    ├── 20260813_init.sql NOT in schema_migrations → apply it
    ├── SQL: CREATE TABLE IF NOT EXISTS ... → creates all 92 tables
    ├── SQL: CREATE INDEX IF NOT EXISTS ... → creates all 121 indexes
    ├── SQL: CREATE TRIGGER IF NOT EXISTS ... → creates all 4 triggers
    ├── SQL: INSERT OR IGNORE INTO ... → seeds essential data
    ├── INSERT INTO schema_migrations → recorded with checksum
    │
    ▼
✅ Full schema + seed data created from single migration
```

## Dead Rows in schema_migrations

After the reset, existing dev databases will have:
- 131 old rows (`001_sales.sql` through `136_processed_webhooks.sql`) — never checked, never removed
- 1 new row (`20260813_init.sql`) — the only actively tracked migration

The 131 old rows are harmless:
- Runner only checks IDs in the registry (which is just `20260813_init.sql`)
- Old rows don't affect performance (checked once at boot, in-memory HashMap)
- Can be cleaned up later with `DELETE FROM schema_migrations WHERE id != '20260813_init.sql'` if desired

## Naming Convention

New format: `YYYYMMDD_description.sql`

Examples:
- `20260813_init.sql` — this reset
- `20260815_add_feature_x.sql` — future migration
- `20260901_fix_index_y.sql` — future migration

Future migrations do **not** need `IF NOT EXISTS` — the runner applies each
migration exactly once and tracks it in `schema_migrations`. Only this init
migration needs idempotency for backward compatibility with existing DBs.
